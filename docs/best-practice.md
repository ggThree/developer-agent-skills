# 最佳实践

## 1. 把请求写成可验证目标

弱请求：“帮我处理一下 Git。”

推荐请求：“审查当前分支相对 `origin/main` 的差异，按 High/Medium/Low 分级，给测试清单和中文 Commit Message，不执行暂存、提交或推送。”

明确基线、输出、授权边界和成功标准，可以显著减少误操作。

## 2. 先确认仓库身份

在多 worktree、子模块或嵌套仓库中，当前目录不一定是目标仓库。执行前确认：

```bash
git rev-parse --show-toplevel
git remote -v
git status --short --branch
```

远端 URL 只用于核对仓库身份，输出报告时应脱敏 URL 中可能存在的凭据。

## 3. 分开审查工作区与暂存区

`git diff` 显示尚未暂存的变化，`git diff --cached` 显示即将提交的变化。二者必须分别审查；“我刚才看过 Diff”不能证明暂存区仍相同。

推荐顺序：

1. `git status --short`；
2. `git diff --stat` 与 `git diff`；
3. 用户确认暂存范围；
4. `git add <精确路径>`；
5. `git diff --cached --stat` 与 `git diff --cached`；
6. 再次确认提交内容。

## 4. 精确暂存

优先使用精确文件路径或 `git add -p`，避免在混合工作区直接使用 `git add .`。未跟踪的环境文件、构建产物和凭据必须先排除。

## 5. 把 fetch 与历史改写分开执行

`fetch` 用于刷新判断依据，不自动合并；执行前说明它会访问网络并更新远端跟踪引用，用户明确禁止网络访问时跳过并标记远端状态未知。`rebase` 和任何 `reset` 会改变本地历史或状态，应在展示分叉关系、工作区状态、备份分支与恢复命令后单独确认。

## 6. 共享历史使用 revert

已经推送、被合并或可能被其他人拉取的提交，优先使用 `git revert` 创建反向提交。只有确认提交未共享、工作区已保护且用户理解影响时，才分析 `reset --soft` 或 `reset --mixed`。

## 7. 发布检查不替代运行验证

静态检查可以发现脏工作区、调试输出、版本漂移、锁文件不一致和 Tag 冲突，但不能证明：

- iOS 真机权限、签名和推送正常；
- Web 浏览器兼容、缓存与路由回退正常；
- Spring 事务、数据库迁移和生产配置正常；
- 外部 API、支付、认证和回调链路正常。

把脚本结论与项目 CI、测试环境、设备回归和业务验收组合使用。

## 8. 报告必须可追踪

每个风险至少包含文件/行、触发条件、影响、建议验证和回滚方式。无法验证的推断要明确标记，不能用模糊的“可能有问题”替代证据。

## 9. 不记录秘密

执行 `remote -v`、查看配置或审查日志时，过滤 URL 凭据、Token、Cookie、证书内容和个人数据。示例统一使用 `[REDACTED_SECRET]`。

## 10. 让仓库保护成为最后防线

在团队仓库启用：

- 受保护默认分支；
- 禁止强制推送；
- 必需 CI 检查；
- CODEOWNERS 或等价审批；
- 最小权限机器人凭据；
- Tag/Release 权限隔离；
- 可恢复备份与发布回滚演练。

Skill 提升决策质量，但不能替代平台权限控制。
