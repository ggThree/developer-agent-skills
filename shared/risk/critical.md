# Critical 风险

## 风险名称

大范围不可恢复损害或主动安全边界失控。

## 风险等级

`Critical`（最高级，立即阻断）。

## 判断依据

满足以下任一条件，且存在可信的可达路径或直接证据时，判定为 Critical：

- 可能造成大范围、不可恢复或恢复成本极高的数据删除、污染、重复记账或密钥泄漏；
- 允许未授权主体取得生产管理权限、跨租户批量访问敏感数据或绕过核心认证；
- 会让生产核心系统全面不可用，且没有经过验证的快速隔离或回滚路径；
- 发布、迁移或 Git 操作会不可逆地覆盖共享历史、生产数据或唯一制品；
- 代码主动关闭 TLS/证书验证、暴露生产私钥，且路径会进入正式环境；
- 安全、合规或资金后果已经发生，继续操作可能扩大损失。

判定需要“严重后果 + 可达证据”。仅凭修改文件敏感、理论攻击可能或代码风格异常，不能直接标为 Critical；证据不足时先标记待确认并执行最短验证。

## 影响范围

- 全部或大量用户、多个租户、核心交易与身份系统；
- 生产数据库、对象存储、密钥、证书、审计记录和共享 Git 历史；
- 法律合规、财务对账、品牌信誉与业务连续性；
- 需要跨开发、测试、安全、运维、业务和管理责任人协同处置。

## 建议操作

1. 立即停止发布、合并、推送、迁移或相关自动化，不继续试错。
2. 保存只读证据：Commit SHA、Diff、时间、日志范围、受影响环境与触发条件；不得传播敏感原文。
3. 隔离影响面，例如关闭 feature flag、撤下入口、暂停消费或切断泄漏凭证；隔离动作本身也需授权。
4. 由明确责任人批准修复与恢复方案，至少进行双人复核。
5. 在隔离环境复现并验证最小修复，覆盖攻击、失败、重复和并发路径。
6. 若涉及凭证泄漏，按安全流程轮换并审计使用记录；删除仓库文本不能使已泄漏凭证重新安全。

## 回滚建议

- 回滚前建立可验证恢复点，记录应用版本、数据库版本、配置、制品与 Git Commit。
- 已共享 Commit 优先使用 `git revert` 保留审计历史；不得用强制推送掩盖事件。
- 数据破坏必须从经过验证的备份恢复或采用经审批的修复脚本，先在副本 dry-run 并核对影响行数。
- 外部副作用（支付、消息、邮件、对象存储、第三方 API）需要独立补偿，代码回滚不会自动撤销。
- 回滚后验证数据一致性、权限边界、错误率、审计日志与核心业务，并持续观察到责任人解除阻断。

## 典型示例

| 场景 | Critical 成立证据 |
| --- | --- |
| 无条件全表删除 | 生产路径可达且缺少条件、备份或事务保护 |
| 管理接口越权 | 普通用户能够批量读取或修改其他租户数据 |
| 私钥泄漏 | 有效生产私钥进入公开历史或可下载产物 |
| 强制覆盖共享历史 | 受保护主分支的大量唯一 Commit 将无法从既有引用恢复 |
| 重复资金处理 | 回调可重复入账且已出现对账差异或高频可触发路径 |

## 降级条件

只有在证据证明路径不可达、影响被可靠隔离、数据可完整恢复且不存在安全扩散后，才能降为 [`high.md`](high.md) 或更低等级。降级理由必须写入 [`../templates/risk_report.md`](../templates/risk_report.md)。
