# 通用代码审查规则

代码审查的目标是找出会改变正确性、安全性、数据一致性、兼容性和可维护性的具体问题，而不是复述 Diff 或评价个人风格。

## 1. 审查基线

开始前明确以下信息：

- 比较对象：工作区、暂存区、Commit 区间或 PR；
- base 与 head 的准确引用；
- 需求、Issue、接口契约或验收标准；
- 项目级规范、构建命令与测试入口；
- 当前工作区是否包含不属于本次审查的修改。

基线不清时可以继续做有限审查，但结论必须标为“证据不足”，不能扩大为整个项目结论。

## 2. 审查顺序

1. 阅读变更统计与文件清单，识别技术栈和影响面；
2. 阅读完整 Diff，不只看新增行；
3. 追踪入口、调用方、类型、状态和错误路径；
4. 检查测试是否覆盖变化行为，而非仅检查测试文件是否存在；
5. 根据项目选择 [`../adapters/`](../adapters/) 的专项清单；
6. 运行最小相关验证，记录真实命令、环境和结果；
7. 在“风险分析”中按严重度输出可操作 Findings；
8. 按固定六节汇总残余风险、回归清单与建议 Commit Message。

## 3. Finding 成立条件

每个 Finding 必须同时具备：

- **可定位**：精确到文件与最小行范围；
- **可触发**：描述输入、状态、平台或时序条件；
- **有后果**：说明用户、数据、安全、兼容或运维影响；
- **有证据**：来自代码路径、契约、日志或可复现实验；
- **可行动**：给出最小修复方向或最短验证方式。

纯偏好、没有行为影响的格式建议、工具自动格式化内容，不应伪装成缺陷。

## 4. 严重度

- `Critical`：可能造成不可接受的安全事件、大范围不可恢复数据损坏或核心生产系统失控，定义见 [`../risk/critical.md`](../risk/critical.md)。
- `High`：常见路径会失败、数据或安全边界受损、发布会被阻断，定义见 [`../risk/high.md`](../risk/high.md)。
- `Medium`：特定条件下功能退化、兼容性或维护成本明显上升，定义见 [`../risk/medium.md`](../risk/medium.md)。
- `Low`：影响有限且有明确绕行方式，但值得低成本修正，定义见 [`../risk/low.md`](../risk/low.md)。

严重度由“影响 × 发生可能性 × 可恢复性”决定，不由修改行数决定。

## 5. 通用检查维度

### 正确性

- 正常、空值、边界、重复、乱序、超时和失败路径；
- 状态是否在所有出口恢复；
- 类型转换、日期时区、精度、编码和枚举兼容；
- 并发、重试、幂等、事务和缓存一致性。

### 安全与隐私

- 身份认证与授权是否区分；
- 输入验证、输出编码、路径和命令注入；
- 日志、错误信息、埋点和测试数据是否泄露敏感信息；
- TLS、证书校验、密钥存储与最小权限。

### 兼容性

- API 请求和响应字段、空值与旧客户端；
- 数据库、配置、依赖锁文件和构建产物；
- 操作系统、浏览器、设备、架构和运行时差异。

### 可维护性

- 是否复用现有组件、服务、类型和错误处理；
- 是否引入重复来源、隐式副作用或难以回滚的耦合；
- 测试是否表达业务行为并能够稳定复现失败。

## 6. 验证纪律

- 只报告实际运行的验证，不把“应通过”写成“已通过”。
- 优先使用项目已有脚本、CI 配置和锁定工具链。
- 失败命令必须保留核心错误信息，并区分代码失败与环境失败。
- 构建成功不等同于运行正确；模拟器成功不等同于真机成功；客户端成功不等同于服务端最终状态正确。

## 7. 输出纪律

使用 [`../templates/review_report.md`](../templates/review_report.md) 的六节固定结构和顺序。Findings 必须位于“风险分析”，并按严重度排列；每条包含位置、证据、触发条件、影响、严重度、置信度、建议操作、回滚建议与验证方法。没有 Findings 时仍需说明审查范围、验证边界和残余风险。

## 8. 非目标

- 不因个人偏好要求大范围重构；
- 不审查与目标 Diff 无关的历史问题，除非变化使其可达或显著加重；
- 不把缺少可选优化当作当前补丁缺陷；
- 不在“仅审查”任务中直接修改文件。
