# 风险报告模板

风险报告用于把“可能有问题”转换为可验证、可决策、可回滚的工程信息。没有触发条件和证据的担忧不得标成确定风险。

## 输出结构

### 风险结论

给出最高风险等级与建议决策：`阻断`、`确认后继续`、`允许继续并跟踪` 或 `可接受`。等级映射遵循 [`../risk/`](../risk/)。

### 风险清单

每项必须包含以下字段：

| 字段 | 内容要求 |
| --- | --- |
| 风险名称 | 用可观察后果命名，例如“迁移失败导致订单状态不可读” |
| 风险等级 | `Critical`、`High`、`Medium` 或 `Low` |
| 判断依据 | Diff、调用链、日志、测试、配置或缺失证据 |
| 触发条件 | 什么输入、环境或操作会使风险发生 |
| 影响范围 | 用户、数据、系统、平台、发布与运维 |
| 建议操作 | 优先最小修复、隔离或验证步骤 |
| 回滚建议 | 回滚命令前置检查、恢复对象和回滚后验证 |
| 责任边界 | 需要开发、测试、产品或运维做出的决定 |

### 验证计划

按风险优先级给出可执行检查，并标明：

- 已执行：写明命令、环境和结果；
- 未执行：写明原因与执行条件；
- 人工检查：写明入口、操作和预期结果。

### 残余风险

说明采取建议操作后仍然存在的限制，例如真实支付账号、物理设备、生产证书或大规模数据才能验证的行为。

## 完整示例

```text
风险结论：High，修复并验证失败分支后再合并。

风险名称：支付回调重复处理导致重复记账
风险等级：High
判断依据：回调服务直接写入流水，未见唯一键或幂等状态检查
触发条件：支付平台重试同一回调
影响范围：订单流水、余额统计、对账任务
建议操作：以平台交易号建立唯一约束，并在事务内检查订单终态
回滚建议：回滚应用版本前保留审计日志；若已产生重复流水，使用经审批的修复脚本按交易号核对，禁止直接删库记录
责任边界：后端确认幂等策略，测试执行重复回调用例，财务确认对账口径
```

涉及 Git 操作的回滚必须遵守 [`../rules/git.md`](../rules/git.md)，不得执行或建议执行 `git reset --hard`。
