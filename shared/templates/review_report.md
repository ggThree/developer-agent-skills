# Diff Review 报告模板

本模板定义代码审查的最小证据集和统一输出顺序。审查对象是明确的 Commit、PR 或 Diff；若基线不明，先说明比较范围，不能把整个工作区状态当作目标变更。

## 报告结构

### 1. 修改摘要

第一句给出 `可合并`、`有条件可合并`、`需要修改` 或 `证据不足` 之一并说明理由；随后列出审查范围、技术栈、关键文件和可观察行为变化。摘要必须可从 Diff 直接定位。

### 2. 修改原因

区分三种信息：

- **事实**：代码、测试、日志或需求中可以直接证明。
- **推断**：根据上下文得到，但没有直接证据。
- **待确认**：会改变结论且当前无法验证。

### 3. 影响范围

至少覆盖入口与调用方、数据与缓存、平台与系统版本、API 与权限、构建与发布，以及回滚后可能保留的副作用。没有证据的范围标为未验证。

### 4. 风险分析

先按严重度从高到低排列可操作 Finding，再列非阻断风险和验证边界。每项包含：

```text
[Critical|High|Medium|Low] 简短标题
位置：文件路径与最小行范围
证据：代码路径、契约或日志
触发条件：输入、状态、平台或时序
影响：用户、数据、兼容性或运维后果
置信度：High、Medium 或 Low
建议操作：最小修复或最短验证方法
回滚建议：恢复范围与副作用
验证方法：可执行命令或手工步骤
```

没有发现时明确写“在本次审查范围内未发现可操作缺陷”，但不能把静态审查等同于运行验证。严重度定义见 [`../risk/critical.md`](../risk/critical.md)、[`../risk/high.md`](../risk/high.md)、[`../risk/medium.md`](../risk/medium.md) 与 [`../risk/low.md`](../risk/low.md)。

### 5. 建议测试

使用“测试目标 → 操作 → 期望结果”描述，优先列出最小自动化命令，再列手工回归。不得宣称未运行的命令已通过。

### 6. 建议 Commit Message

基于实际 Diff 给出一条中文 `Conventional Commit`；若改动不可作为单一原子提交，先给出拆分建议。格式参考 [`commit_cn.md`](commit_cn.md)。

## 完整示例

```text
修改摘要：需要修改。登录页新增短信验证码发送逻辑，但失败分支未恢复 loading，会让用户无法再次提交。

修改原因：事实是成功回调显式恢复按钮；失败路径没有同等处理。需求动机未在 Diff 中说明。

影响范围：影响登录页验证码发送入口和弱网失败恢复；服务端接口未变。

[High] 请求失败后发送按钮永久禁用
位置：src/views/login/SmsLogin.vue:88
证据：loading 在请求前设为 true，仅成功分支设回 false；reject 路径直接进入 catch。
触发条件：接口超时、500 或网络断开。
影响：弱网或服务端错误后，当前页面无法再次发送验证码。
置信度：High
建议操作：在 finally 中统一恢复 loading。
回滚建议：回退本次验证码状态管理改动。
验证方法：补充 reject 分支测试并执行登录模块测试。

建议测试：模拟 500 响应 → 点击发送 → 错误提示后按钮恢复可用。
建议 Commit Message：fix(auth): 恢复验证码失败后的发送状态
```

各技术栈的专项检查由 [`../adapters/`](../adapters/) 选择，通用审查规则见 [`../rules/review-rule.md`](../rules/review-rule.md)。
