# 示例：Objective-C Diff 审查

## 用户输入

```text
$review-diff 审查当前 iOS 差异。问题是从后台回到前台后偶发重复请求，不改代码。
```

## 识别结果

- `*.m`、`*.h` 与 `.xcodeproj` 表明这是 Objective-C iOS 项目。
- 差异涉及 `UIApplicationDidBecomeActiveNotification` 注册与网络请求入口。
- 本次请求是只读审查，不授权修改文件。

## 输出示例

### 修改摘要

控制器在 `viewDidLoad` 注册前台通知，并在回调中重新加载账户数据；同时保留了 `viewWillAppear:` 中的加载调用。

### 修改原因

从差异和用户描述推断，改动用于解决后台期间数据失效。但仓库证据尚不能证明服务端是否要求每次激活都刷新。

### 影响范围

- 账户首页首次展示；
- 页面仍在导航栈时的前后台切换；
- 请求 loading 状态与错误提示；
- 通知观察者生命周期。

### 风险分析

**High：同一前台事件可能触发两条请求路径**

- 证据：`viewWillAppear:` 和激活通知都调用 `reloadAccount`，且没有去重或请求中状态判断。
- 触发条件：应用回前台时控制器同时重新可见。
- 影响：重复接口请求、状态覆盖、重复错误提示；若接口有副作用，影响会更高。
- 建议：先在请求入口记录 request id、调用来源和时间，真机复现一次前后台切换。
- 回滚：撤销通知回调中的新增请求调用，保留原有页面生命周期逻辑。

**Medium：观察者移除方式需要确认**

- 证据：新增注册代码，但当前 Diff 未展示 `dealloc` 或 token 生命周期。
- 不确定性：若项目使用 block observer 并由属性持有，需检查 token 是否移除；selector API 在现代系统上的行为不同，不能仅凭局部 Diff 下结论。

### 建议测试

1. 冷启动首次进入只发起一次请求；
2. 前后台切换 5 次，每次请求数符合产品预期；
3. 请求未完成时再次切后台/前台，不出现并发覆盖；
4. 页面退出后前后台切换，不再触发该控制器请求；
5. 主线程更新 UI，弱网错误提示只出现一次。

### 建议 Commit Message

```text
fix(account): 避免前台恢复时重复刷新账户数据
```

该审查只确认静态风险；未运行真机、网络代理或服务端日志验证。
